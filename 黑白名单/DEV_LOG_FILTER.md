## 一、需求工程（Spec-First 规格优先）

### 1. 业务意图

基于实训计划书"拓展功能需求"中"支持 IP / 端口黑白名单、线程数、发包间隔自定义"的要求，以及用户三项明确架构决策（解析后过滤、白名单优先、内置+外部配置结合），构建一款**高内聚、低耦合、可配置、可反馈**的扫描目标过滤模块，作为解析层与扫描引擎之间的安全闸门。

核心意图：在扫描执行前拦截敏感目标，防止误操作系统保留地址/端口，同时通过白名单机制实现"默认拒绝、明确允许"的安全策略。

### 2. 功能性需求（结构化无歧义）

| 编号 | 需求项 | 规格说明 |
|------|--------|----------|
| FR-01 | 解析后过滤 | 在 IPParser/PortParser 解析完成后、扫描执行前进行过滤 |
| FR-02 | 黑名单模式 | 默认禁止扫描指定 IP/端口，其余放行 |
| FR-03 | 白名单模式 | 明确允许指定 IP/端口，优先级高于黑名单 |
| FR-04 | 白名单优先策略 | 同时命中黑白名单时，白名单胜出放行 |
| FR-05 | 内置兜底规则 | 系统保留地址（广播、组播）和端口（Echo、Chargen 等）硬编码保护 |
| FR-06 | 外部配置加载 | 支持从 JSON 文件加载用户自定义规则 |
| FR-07 | 动态规则管理 | GUI 支持运行时增删规则，实时生效 |
| FR-08 | 配置持久化 | 规则变更后自动保存到 JSON，重启恢复 |
| FR-09 | 过滤反馈 | 返回详细过滤日志（被过滤项、原因、规则来源），供 GUI 展示 |
| FR-10 | 过滤结果不可变 | 返回 FrozenSet，保证多线程环境下不被意外修改 |

### 3. 非功能性需求（量化约束）

| 编号 | 需求项 | 量化指标 |
|------|--------|----------|
| NFR-01 | 模块内聚性 | 所有过滤逻辑集中在 `core/filter.py`，不泄露到 GUI/扫描器 |
| NFR-02 | 模块耦合度 | GUI 层仅依赖 `ScanFilter` 和 `FilterResult`，不感知内部规则存储结构 |
| NFR-03 | 零副作用 | 过滤操作不修改输入集合，返回新对象 |
| NFR-04 | 线程安全 | 返回不可变集合（FrozenSet）与不可变数据类（frozen=True） |
| NFR-05 | 可测试性 | 4 项单元测试，覆盖正常路径、白名单优先、配置加载、边界值 |
| NFR-06 | 异常一致性 | 过滤异常继承项目根异常 `ScannerError` |
| NFR-07 | 配置隔离 | 内置规则与用户规则分离，内置规则不可删除 |

### 4. 领域字典（统一术语）

| 术语 | 定义 |
|------|------|
| FrozenSet | 不可变集合，消除多线程副作用 |
| frozen=True | dataclass 装饰器，禁止运行时修改字段 |
| FilterResult | 不可变过滤结果契约，含允许集合与过滤日志 |
| FilterLog | 单条过滤记录（被过滤项、类型、原因、规则来源） |
| 白名单优先 | 命中白名单即放行，即使同时命中黑名单 |
| 内置兜底 | 系统保留地址/端口硬编码，不可删除，最后一道防线 |
| 解析后过滤 | 在字符串解析为结构化集合后执行过滤，而非输入阶段 |
| 规则来源 | builtin（内置）/ config（用户配置）/ whitelist（白名单覆盖） |

### 5. BDD 行为规约（Given-When-Then）

#### 场景 1：内置黑名单过滤
Given 用户输入目标包含 "192.168.1.1, 224.0.0.1, 255.255.255.255" 和端口 "80, 7, 443"  
When 执行 ScanFilter.apply()  
Then "224.0.0.1" 和 "255.255.255.255" 被过滤（组播/广播地址）  
And 端口 "7" 被过滤（Echo 服务，系统保留）  
And "192.168.1.1"、"80"、"443" 正常放行  
And 过滤日志包含原因和规则来源

#### 场景 2：自定义黑名单
Given 用户配置 IP 黑名单 {"192.168.1.1"}，端口黑名单 {3306}  
When 执行过滤  
Then "192.168.1.1" 被过滤（用户自定义黑名单）  
And 端口 "3306" 被过滤（用户自定义黑名单）  
And 其他目标正常放行

#### 场景 3：白名单优先策略（核心策略）
Given IP "192.168.1.1" 同时在黑名单和白名单中  
When 执行过滤  
Then "192.168.1.1" 被放行（白名单优先于黑名单）  
And 过滤日志为空（无被过滤项）

#### 场景 4：配置持久化
Given 用户通过 GUI 添加 "10.0.0.99" 到 IP 黑名单  
When 点击"保存并应用"  
Then 规则保存到 scan_rules.json  
And 下次启动自动加载该规则  
And 实时生效（下一次扫描即应用）

## 二、架构设计（Architecture as Code）

### 1. 技术栈

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 语言 | Python 3.8+ | 类型注解、dataclass、ipaddress |
| 网络 | ipaddress | IP 地址验证、组播/广播/保留地址检测 |
| 配置 | json | 用户规则持久化 |
| GUI | PyQt6 | 规则管理对话框 |
| 测试 | unittest | 标准测试框架 |

### 2. 架构模式

三层模块化架构：
- **`core/filter.py`**：过滤引擎层（规则加载、过滤逻辑、结果契约）
- **`gui/filter_dialog.py`**：规则管理 GUI（增删改查、持久化触发）
- **`gui/main_window_filter_patch.py`**：集成补丁说明（与现有 MainWindow 对接）

### 3. 架构决策记录 ADR

#### ADR-001：解析后过滤（Post-Parse Filtering）

- **Context**：过滤时机选择——输入字符串阶段 vs 解析后集合阶段
- **Decision**：采用解析后过滤，接收 FrozenSet[str] 和 FrozenSet[int]
- **Status**：已完成
- **Consequences**：
  - 优点：过滤逻辑与解析逻辑解耦，可独立测试；能处理解析后的精确 IP 列表（如 CIDR 展开后的所有 IP）
  - 缺点：需要先完成解析才能过滤，大网段解析可能消耗内存（但已有 100,000 任务量上限防护）

#### ADR-002：白名单优先策略（Whitelist Precedence）

- **Context**：黑白名单冲突时的优先级判定
- **Decision**：白名单优先级高于黑名单，命中白名单即放行
- **Status**：已完成
- **Consequences**：
  - 优点：符合安全领域"默认拒绝、明确允许"的最佳实践；黑名单作为兜底，白名单作为例外
  - 缺点：用户可能误将危险地址加入白名单，需配合合规提示

#### ADR-003：内置+外部配置分离（Builtin + External Config）

- **Context**：系统保留规则与用户自定义规则的管理方式
- **Decision**：内置规则硬编码（不可删除），用户规则外部 JSON 存储（可增删）
- **Status**：已完成
- **Consequences**：
  - 优点：内置规则作为安全底线始终生效；用户规则灵活可配置；两者合并时内置规则不可被用户误删
  - 缺点：用户无法覆盖内置规则（设计意图，防止误操作）

#### ADR-004：不可变返回类型（Immutable FilterResult）

- **Context**：过滤结果在多线程环境下的安全性
- **Decision**：FilterResult 使用 frozen=True dataclass，allowed_targets/allowed_ports 使用 FrozenSet
- **Status**：已完成
- **Consequences**：
  - 优点：线程安全，下游扫描器无法意外修改过滤结果
  - 缺点：需要创建新对象，内存开销微小（可忽略）

#### ADR-005：GUI 与过滤引擎解耦（Dialog-Engine Decoupling）

- **Context**：FilterDialog 如何与 MainWindow 和 ScanFilter 交互
- **Decision**：FilterDialog 持有 ScanFilter 实例副本，通过 `rules_changed` 信号通知 MainWindow；MainWindow 通过回调更新自身持有的 ScanFilter 引用
- **Status**：已完成
- **Consequences**：
  - 优点：FilterDialog 可独立测试、复用；不直接操作 MainWindow 状态
  - 缺点：需要信号/回调机制，增加了少量代码复杂度

### 5. 多模型对抗审查结论

- 必须采用解析后过滤，输入阶段过滤无法处理 CIDR 展开后的具体 IP
- 必须白名单优先，符合安全领域"明确允许"原则
- 必须内置+外部分离，防止用户误删系统保留规则导致安全风险
- 必须不可变返回类型，保证多线程扫描器不意外修改过滤结果
- 必须 GUI 与引擎解耦，FilterDialog 应可独立复用

## 三、上下文工程（Context Engineering）

### 1. 核心提示词（Prompt = 源码）

高内聚低耦合、解析后过滤、白名单优先、内置兜底、外部 JSON 配置、动态增删、实时生效、不可变返回、FrozenSet、frozen=True、FilterLog、FilterResult、RuleLoader、ScanFilter、FilterDialog、PyQt6、信号驱动、线程安全。

### 2. 上下文约束

- 过滤时机：解析后，接收 FrozenSet[str] + FrozenSet[int]
- 优先级：白名单 > 内置黑名单 > 自定义黑名单 > 放行
- 内置 IP 黑名单：广播地址(255.255.255.255)、组播地址(224.0.0.0/4)、保留地址
- 内置端口黑名单：0, 7, 9, 13, 17, 19, 37, 111, 512-515, 540
- 配置文件：scan_rules.json
- 禁止第三方库（GUI 层除外）
- 最小权限运行

### 3. 人工修正点

- 过滤日志从简单字符串列表升级为 `FilterLog` 结构化对象，支持规则来源追溯
- `ScanFilter` 从函数式改为类式，支持实例级状态管理和动态增删
- `FilterDialog` 从 MainWindow 内嵌改为独立对话框，通过信号通信
- 内置规则从可修改改为只读，防止用户误删系统保留规则
- 添加 `_is_valid_ip_or_cidr` 静态校验，防止 GUI 输入非法规则

### 4. 上下文防腐化措施

- 干净上下文启动，无冗余历史导入
- 语义化命名（ScanFilter/FilterResult/FilterLog/RuleLoader/FilterDialog）
- 无 UUID 乱码，无魔法数（端口/地址范围使用命名常量）
- 类型注解完整覆盖

## 七、合规声明

本模块仅限授权内网安全测试使用。黑白名单过滤旨在防止误操作系统保留地址/端口，降低扫描行为的合规风险。过滤功能本身不构成对扫描行为的限制或鼓励，用户仍需确保所有扫描目标均已获得明确授权。
